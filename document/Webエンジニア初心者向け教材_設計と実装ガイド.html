第1章：モダンWeb開発のアーキテクチャ

1.1 なぜ Next.js と TypeScript を選ぶのか？

現代のWeb開発でデファクトスタンダード（標準）となっているのが、Reactベースのフルスタックフレームワークである Next.js と、静的型付け言語の TypeScript です。

  • TypeScriptの利点（安全性の向上）: 変数や関数の受け渡しにおいて「型（設計図）」を定義することで、タイポ（打ち間違い）やデータ構造の不一致を実行前にパソコンが検知してくれます。
  • Next.jsの利点（開発効率の最大化）: 画面の表示（フロントエンド）とAPIサーバー（バックエンド）を1つのプロジェクトで同時に扱え、高速な画面遷移が簡単に作れます。

1.2 App Routerの「フォルダ＝URL」の仕組み

Next.jsの最大の特徴が「App Router（アップ・ルーター）」です。src/app/ 配下のフォルダ構造が、そのままWebサイトのアドレス（URL）になります。

ファイルパス ブラウザのURL 画面の役割
src/app/page.tsx / ダッシュボード（トップ画面）
src/app/events/page.tsx /events 日程調整一覧画面
src/app/events/new/page.tsx /events/new 新規日程調整の作成フォーム
src/app/events/[id]/page.tsx /events/ev-1 など イベント詳細画面（[id] は動的パラメータ）
src/app/events/[id]/respond/page.tsx /events/ev-1/respond 日程・場所の回答入力画面
src/app/events/[id]/vote/page.tsx /events/ev-1/vote 集計結果カード & 最終投票画面
src/app/locations/page.tsx /locations 練習場所一覧 & Google Map埋め込み
src/app/profile/page.tsx /profile プロフィール設定画面
src/app/admin/users/page.tsx /admin/users 管理者専用メンバー追加画面

第2章：要件定義から型定義への落とし込み

2.1 「データの最小化原則」の実践

開発途中、ユーザーから「セキュリティが心配なので個人情報は絶対に持たせたくない。氏名やメールアドレス、パートは削除してほしい」という重要な要望がありました。

セキュリティの最も強力な防御策は、「攻撃されても漏洩して困るデータ自体を最初から保存しないこと」です（データ最小化の原則）。これをTypeScriptの型定義にどう反映したかを見てみましょう。 

// src/types/index.ts より抜粋
export interface User {
  id: string;        // メンバー固有のログインID (例: "ken", "misaki")
  password: string;  // ログインパスワード
  nickname: string;  // あだ名・バンド内表示名
  bio?: string;      // 自己紹介・ひとこと (任意)
  isAdmin?: boolean; // 管理者権限フラグ (メンバー追加権限)
}

氏名やメールアドレスを排除し、ログインとバンド内の呼称に必要な最小限の項目に絞り込みました。また、部外者が勝手に登録できないよう、管理者がアカウントを発行する権限フラグ（isAdmin）を設けました。

2.2 状態の厳密な型定義（Union Type）

日程調整イベントの進行状態（ステータス）は、文字列なら何でも良いわけではありません。「決められた特定の状態」しか取れないように定義します。 

export type EventStatus = 
  | "open"        // 回答受付中（メンバーが回答可能）
  | "aggregated"  // 集計完了（条件一致候補が0件だった状態）
  | "voting"      // 最終投票中（複数候補から投票）
  | "confirmed"   // 確定済み（練習日時・場所が決定）
  | "completed"   // 練習終了（日時を経過した過去の記録）
  | "cancelled";  // 中止

このように Union Type（共用体型）を使うと、例えば status = "finish" と間違えて書いた瞬間に TypeScript が「そんなステータスは存在しません」とエラーを出してくれるため、バグを未然に防ぐことができます。

第3章：状態管理と認証ガードの仕組み

3.1 React Context（共有の記憶部屋）

Webアプリでは、「いま誰がログインしているか？」「日程調整のリスト」といったデータを、複数の画面で共有する必要があります。

バケツリレー問題の解決：
親コンポーネントから子、孫へと props（引数）を手渡しし続けるのは保守性が低下します。そこで AppContext という「アプリ共通の記憶部屋」を作り、どの画面からでも直接データを読み書きできるようにしました。 
// どのコンポーネントからでも1行でデータにアクセスできる
const { currentUser, events, updateEventStatus } = useApp();

3.2 未ログインを遮断する「認証ガード（AuthGuard）」

「ログインしていなければ絶対に中身の画面を見せない」という仕組みは、ClientProviders.tsx の中で以下のようにシンプルに実現されています。 

function AuthContent({ children }: { children: React.ReactNode }) {
  const { currentUser } = useApp();

  // currentUser が null（未ログイン）なら、画面の中身ではなくログインフォームを返す！
  if (!currentUser) {
    return <LoginForm />;
  }

  // ログイン済みならヘッダーと各ページを表示
  return (
    <>
      <Header />
      <main>{children}</main>
    </>
  );
}

第4章：コアアルゴリズム徹底解説（集計とタイブレーク）

4.1 時間帯と練習場所の最大人数集計ロジック

本アプリで最も高度なプログラミングが要求されたのが、src/lib/aggregation.ts の集計アルゴリズムです。

アルゴリズムの思考ステップ：
1. スロットの離散化: 自由入力された時間帯を「30分刻み」のコマに分解する。
2. スライディングウィンドウ: 要求された練習時間（例: 2時間＝4コマ）の長方形を、朝から夜まで30分ずつスライドさせて走査する。
3. 共通条件判定: その時間枠を完全にカバーし、かつ「同じスタジオ」が利用可能なメンバーを数える。
4. 最大人数の抽出: 全組み合わせの中で、最も人数の多かった候補枠だけをフィルタリングする。

4.2 民主的な最終投票と完全同票タイブレーク設計

参加可能人数が最大の候補が複数あった場合、参加可能メンバーによる最終投票を行います。ここには以下のような厳密なビジネスルールが組み込まれています：

  1. 投票期限の遵守: 投票期限中は、幹事であっても途中で日程を確定することはできない（全員の投票機会を守るため）。
  2. 期限終了時の自動確定: 期限が到来したとき、単独1位の候補があればシステムが自動で確定状態（confirmed）へ移行させる。
  3. 希望順位スコアによる第1次タイブレーク: 最多得票が同数だった場合、各メンバーが回答時に付けた「練習場所の希望順位スコア（第1希望=3点、第2希望=2点、第3希望=1点）」の合計点を比較し、高い方を優先確定する。
  4. 幹事の最終決定権（第2次タイブレーク）: 得票数も場所スコアも全く同じ「完全同点」の場合に限り、幹事画面に対象候補への「幹事決定で確定する」ボタンが出現する。
// 完全同票判定のコードロジック（vote/page.tsx より）
const isTieVote = topVotedCandidates.length > 1;

if (isTieVote) {
  // 場所スコアの最高点を求める
  maxScoreInTop = Math.max(...topVotedCandidates.map((c) => c.priorityScore));
  finalTieCandidates = topVotedCandidates.filter((c) => c.priorityScore === maxScoreInTop);
  
  if (finalTieCandidates.length === 1) {
    // 場所スコアで決着！優先候補として確定
    scorePriorityWinner = finalTieCandidates[0];
  }
}

// 得票数も場所スコアも同点の候補が複数ある場合のみ、幹事決定フラグが立つ！
const isCompleteTie = isTieVote && finalTieCandidates.length > 1;

第5章：現場で役立つUI/UXテクニック

5.1 Google Map とのシームレスな連動

練習場所一覧画面（/locations）では、右側に Google Map をインライン埋め込みしています。APIキーを消費せずに安全に地図を表示するため、Google Maps の Embed URL を動的に生成しています： 

const embedUrl = `https://maps.google.com/maps?q=${encodeURIComponent(query)}&t=&z=15&output=embed`;

さらに、日程調整詳細画面にある練習場所名をクリックすると、/locations?select=loc-1 のように URL パラメータ付きで遷移します。練習場所画面では useSearchParams() でこの ID を取得し、該当の場所を自動でハイライトして地図の中心を合わせる親切なUXを実現しています。

5.2 練習終了（completed）ステータスの自動遷移

確定した練習日程の終了時刻を過ぎると、システムが自動的にステータスを「練習終了」へと更新します。これにより、確定した練習枠がダッシュボードの「過去の記録」へとアーカイブされ、将来的な「振り返りチャットや音源共有」への布石となっています。

第6章：新人エンジニアがつまずきやすいトラブル解説

6.1 「コマンドが認識されない！」環境変数PATHの正体

Node.jsをインストールした直後、ターミナルで npm を実行しても「認識されません」とエラーが出ました。

⚠️ なぜ起きたのか？
Windowsは「環境変数 PATH（パス）」という検索リストを見てプログラムを探します。Node.jsをインストールするとWindows本体のリストは更新されますが、「すでに開いていたターミナル」は古いリストをメモリに保持したままになっています。そのため、ターミナルを開き直す（または再起動する）ことで最新のリストが反映され、コマンドが使えるようになります。

6.2 「デザインが当たらない！」CSSビルドの仕組み

Next.js 16 と Tailwind CSS v4 の組み合わせにおいて、CSSが生成されず文字だけの画面になってしまう問題が発生しました。

最新のツール同士では、設定の相性によって内部プロセス（Turbopackの外部ローダー等）がうまく起動しないケースがあります。今回は、最も確実で安定した @tailwindcss/cli を導入し、「あらかじめCSSをビルドしてからNext.jsを起動する」 という確実なビルドチェーンを package.json に構築することで解決しました。 

"scripts": {
  "build:css": "tailwindcss -i ./src/styles/input.css -o ./src/app/globals.css",
  "dev": "npm run build:css && next dev",
  "build": "npm run build:css && next build"
}
